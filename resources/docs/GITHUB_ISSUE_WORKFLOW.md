# GitHub Issue 工作流(问题与规划的全程留痕)

> 适用前提:项目托管在 GitHub。非 GitHub 托管(GitLab、内网 Git 等)的项目不适用本约定,按各平台等价机制(Issue/MR)自行对应。

## 核心原则

开发与维护中每一次"值得回溯的事"都落在 GitHub issue 上:问题先立案再修复,规划先立项再实现;完成并验证后,把方案与证据写回 issue 并关闭。issue 列表即项目的**维护台账**——半年后任何人(包括未来的自己和 agent)都能查到"当时为什么改、怎么验证的"。

## 记还是不记(判据)

**必须开 issue**——满足任一条:
- BUG 修复(含门禁绕过、回归修复);
- 行为变更(接口、输出、配置语义、依赖版本);
- 需要验证的改动(效果须以命令/测试结果证实);
- 任何规划项(想做还没做的事,先立案防遗忘)。

一句话判据:**"半年后需要回查'为什么改、怎么验证的'吗?"——需要,就开。**

**不用开 issue**——无行为影响的机械改动,commit message 说清即可:
- 笔误、注释、格式化;
- 文档措辞微调;
- 文件改名、变量/函数改名等纯重命名。

## 分类与标签

| 类型 | label(GitHub 自带) | 标题约定 |
|---|---|---|
| 问题/BUG | `bug` | 现象 + 位置,如「Stop 层评审在空仓库下报错」 |
| 规划/新增 | `enhancement` | 前缀 `[规划]`,如「[规划] 支持 Gradle 项目」 |

不新造 label;要区分"规划中/进行中",改标题前缀即可(实现时去掉 `[规划]`)。

## 生命周期

```
开 issue(现象或目标 + 验收标准)
  → 开发(分支/提交关联 issue 编号,如 #12)
  → 验证(命令与结果如实记录;未验证的如实标注)
  → 关闭评论(按下方模板)
  → close
```

验收标准在开 issue 时就写清——"怎么算完成"不留给关闭时临时解释。

## 关闭评论模板(固定三段)

```markdown
**解决方案**:改了什么、为什么这么改;关联 commit/PR 编号。
**验证证据**:实际运行的命令与结果;测试/门禁输出摘要。
**影响面**:可选——波及的调用方/配置/文档,无需则省略。
```

前两段缺一不可:只有"已修复"没有证据的关闭视为未完成。

## 给 agent 的指令块(手动引用)

把下面这段直接发给 agent,即让其按本约定工作:

> 按 `docs/GITHUB_ISSUE_WORKFLOW.md` 执行开发与维护:动手解决任何"必须开 issue"的问题前,先查有无在案 issue,没有则创建(现象 + 验收标准);实现任何规划前同样先立项。完成并验证后,在 issue 里按三段模板(解决方案/验证证据/影响面)回答并关闭。操作通道自选(github MCP / gh CLI / 网页),但关闭评论必须含模板三段。
