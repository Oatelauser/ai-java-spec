# 版本发布流程(通用模板)

**适用**:语义化版本(X.Y.Z)、主干开发、有 CI 门禁的项目。
**核心理念**:发布日的全部动作是"核对与落盘",不出现"补救"——质量与文档在
开发期累积,走到发布日只剩执行。

**流程总览**:

```
周期开头:收口(基线上移)+ 版本规划(定主题与范围)
开发期:  特性随合随记 CHANGELOG 待发布段
发布日:  版本冻结 → 文档同步 → 双臂验证 → 提交 → push → CI 绿 → 打 tag
```

## 阶段 0:版本规划(周期开头)

**输入**:产品路线图、已决策待实现的架构决策记录(ADR)、上一周期顺延项。

**产出(落在仓库,而非口头)**:

| 产出 | 说明 |
|---|---|
| 版本号与主题 | `X.Y.Z` + 一句话主题,说明本版为什么存在 |
| 范围清单 | 做什么 + **显式列"本版不做"**防蔓延;未列入的留在候选池 |
| CHANGELOG 待发布段 | 预开 `## X.Y.Z(待发布)`,特性合入即记,发布日只核对不补写 |
| 架构决策先行 | 涉架构的特性先写 ADR 并定稿,再动工 |

**版本号判定**(semver):破坏公共契约 → 主版本;向后兼容的新增能力 → 次版本;
仅修复 → 修订号。0.x 阶段公共契约可破坏,但须集中列明替代用法。

**单特性入版门槛(完成定义)**:实现 + 测试通过 + 文档同步 + CHANGELOG 条目,
差一条即顺延下周期。**宁裁勿凑**:范围只减不增;中途裁掉的特性 CHANGELOG
不留痕(用户从未见过),路线图状态不翻转即自动回候选池;确需追加,回本阶段
重评(可能连带重新验证与文档重同步)。

## 阶段 1:版本冻结

冻结封两样东西:

1. **版本号落盘**——所有版本号出现点一次性升级:
   - 构建文件(根 + 全部子模块;子模块版本常嵌在继承结构里,逐个确认)
   - 示例/脚手架工程(工程自身版本 + 引用本项目的依赖属性,通常两处)
   - 文档中的版本号留给阶段 2,不在本步改
   - **兼容性对比基线引用不要动**:若有 API 兼容性对比工具,其"旧版本"锚点
     仍指上一个发布 tag,误升会让 old==new 恒零差异,护栏静默失效
2. **范围封口**——此后只接受修复与文档改动,不合新特性(要合,回阶段 0 重评)。

**惯例建议**:开发期构建文件一直携带上一个已发布版本号,升版只发生在发布
提交里——版本变更在 git 历史里是单点,可审计、可回溯。

## 阶段 2:文档同步

| 对象 | 检查点 |
|---|---|
| CHANGELOG | 待发布段补发布日期定稿;按用户可见视角分类(新增/变更/移除/修复) |
| README | 版本徽章、依赖/安装片段中的版本号与产物文件名、特性一览时效性、量化口径(如测试总数) |
| 用户手册 | 头部版本行、代码片段中的版本与产物文件名 |
| 路线图 | 已交付特性状态翻转;顺手清掉与实现不符的旧条目 |
| 设计文档 | 抽查有无与新版本事实不符的陈述 |

**原则**:文档随特性在同一开发周期内落盘,发布日只做核对与一致性抽查,
不做补写。

## 阶段 3:双臂验证(发布门槛)

**定义**:同一套验收测试,在两条独立路径下各跑一遍,差分一致才放行:

- **生产臂**:默认配置 / 新实现路径(用户实际走的路)
- **参照臂**:保守配置 / 旧实现或参照实现(已知正确性的锚点)

**为什么双臂**:单臂全绿只证明"测试通过";双臂一致额外证明"行为符合预期
参照",能抓住单臂下自洽但整体跑偏的回归。

**配套门槛**(按项目裁剪):

- **交付前 AI 全量评审**:上一版本 tag..本版本 diff 全量过一遍 delegate 评审(`/delegate-review` 传范围参数),发现清零或逐条注明豁免理由
- 全量测试 + 静态检查(lint / 格式 / 依赖审计)0 失败
- API 兼容性判定符合预期:纯新增 = 次版本级变更;**有意移除公共 API** 须
  三件套——对比工具加豁免 + CHANGELOG 列明替代用法 + 下周期基线上移时删除豁免
- 多环境矩阵:本地跑主力环境,其余环境交给 CI

## 阶段 4:提交 → push → CI 绿 → 打 tag

```bash
git commit -m "chore: release X.Y.Z (version freeze, docs sync)"  # 提交体附验证证据
git push origin main
# 等 CI 绿(矩阵环境本地未必都覆盖),再打 tag
git tag -a vX.Y.Z -m "<项目名> X.Y.Z: 一段式摘要——特性 + 兼容性判定>"
git push origin vX.Y.Z
```

要点:

- **提交体附验证证据**:两臂结果、兼容性判定、验证环境——发布提交是未来
  排查"这版怎么发的"的第一入口
- **tag 打在 CI 绿之后**:CI 红 → 修复走新提交、重新过本阶段;**已推送的
  tag 不移动**——它是下游消费者与对比工具的锚点
- 用 **annotated tag**(带 message 与元数据),不用轻量 tag
- 网络瞬断导致 push 部分送达时,以 `git status -sb` 的 ahead 计数与
  `git ls-remote` 对账,恢复后原命令重推(git 自动去重)

## 阶段 5:发布后收口(下周期开头,回到阶段 0)

- **对比基线上移**到新 tag:兼容性工具的旧版本锚点、CI 里的基线自举命令、
  构建文件注释中的"当前版本"字样,一处不漏
- **删除已到期的豁免**(阶段 3 三件套的第三件)
- 预开下一版 CHANGELOG 待发布段 → 回到阶段 0

## 发布日核对单(一屏)

1. 工作区干净;规划范围全部合入或已明确裁剪
2. 冻结:全部版本号出现点已升;兼容性基线引用一字未动
3. 文档:CHANGELOG 补日期;README / 手册版本引用;路线图状态翻转
4. 全量评审:上一版本..本版本 diff 的 AI 评审完成,发现清零或注明豁免
5. 双臂:生产臂 + 参照臂全绿;API 兼容判定符合预期
6. 提交(附证据)→ push → CI 绿 → annotated tag → push tag

## 常见陷阱

1. **版本号出现点漏改**:示例工程、脚手架、文档代码片段最常漏——收尾用
   全局搜索旧版本号核对清零
2. **顺手升了对比基线**:护栏 old==new 恒零差异、静默失效——基线只在收口
   阶段(阶段 5)动
3. **本地构建覆盖基线构件**:本地仓库里为对比工具安装的旧版本 jar 会被日常
   install 覆盖,判定可疑时从 tag 重新自举安装
4. **冻结后塞特性**:范围封口的意义就在于此——塞入 = 回到规划重评 + 全部
   验证重跑,成本摆在那里,自然倒逼"宁裁勿凑"
5. **CI 红了移动 tag**:永不移动已推送的 tag,修复走新提交
